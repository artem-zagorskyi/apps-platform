# Identity module

The identity module answers three questions: who is this user, how do they
prove it on every request, and how is their progress kept when they change
devices. A user never fills anything in on first launch: the app gets an
anonymous account immediately and can link Google (and later Apple) at any time.

Code: `platform/src/modules/identity/` and `platform/src/modules/apps/`.

## Concepts

| Concept       | Meaning |
|---------------|---------|
| App           | A product. One `app_id` across Android and iOS |
| User          | A person inside one app. Just an id; its `id` never changes |
| Installation  | One install of the app on one device. Its id is generated by the device. Can move to another user (logout, merge) |
| Auth identity | A Google or Apple account linked to a user. At most one per provider per user |
| Session       | One refresh token. Rotated on every use |
| Token family  | All sessions descended from one sign-in, sharing `family_id` |
| Nonce         | One-time value bound to an installation, embedded by Google/Apple into their ID token |
| Merge         | Folding an anonymous user into an existing user who owns the provider account |

## Data model

### Schema `apps`

| Table              | Purpose | Notes |
|--------------------|---------|-------|
| `apps`             | Products | `slug` unique, `status` `active`/`disabled`. Apps are disabled, never deleted |
| `app_platforms`    | Package name / bundle ID per platform | PK `(app_id, platform)` |
| `oauth_clients`    | Client IDs accepted in Google / Apple tokens | FK `(app_id, platform)` → `app_platforms`; unique `(app_id, provider, client_id)` |
| `consent_policies` | Consent rule per region | `mode`: `none`, `optional`, `consent_or_pay`; `reprompt_after_days` default 180; unique `(app_id, region)` |

Shared enums: `platform` (`android`, `ios`), `auth_provider` (`google`, `apple`).

### Schema `identity`

**`users`**: `id`, `app_id`, `status` (`active`, `merged`, `deletion_pending`,
`deleted`), `merged_into`, `created_at`, `deletion_requested_at`,
`deletion_scheduled_at`, `deleted_at`.

- Unique `(id, app_id)`: target of composite foreign keys from other tables.
- `merged_into` must point to a user of the same app.
- Check: `merged_into` is set exactly when `status = 'merged'`.
- Partial index on `deletion_scheduled_at` for users pending deletion.

**`installations`**: `id` (from the device), `app_id`, `user_id`, `platform`,
`app_version`, `app_build`, `os_version`, device details, `ad_tracking`,
`country`, `region`, `city`, `geo_lat`, `geo_lon`, `created_at`, `updated_at`,
`last_seen_at`.

- `(user_id, app_id)` → `users`; `(app_id, platform)` → `app_platforms`.
- App version, build and OS version are always required. Device details
  (manufacturer, model, screen, RAM, storage, locale, timezone, install source,
  notifications) are nullable: filled only with analytics consent.
- Geo fields are derived from the IP on the server; the IP is never stored.
- `last_seen_at` is updated on every refresh.

**`auth_identities`**: `user_id`, `app_id`, `provider`, `provider_subject`,
`email`, `email_verified`, `email_is_private_relay`, `apple_refresh_token`
(encrypted, for revocation), `created_at`, `last_used_at`.

- Unique `(app_id, provider, provider_subject)`: one provider account belongs
  to one user per app.
- Unique `(user_id, provider)`: one account per provider per user.
- `email_verified` is copied from the provider token, we never verify emails
  ourselves. Do not trust an unverified email for linking or messaging.
- Email fields are updated only when the provider sends an email (Apple sends
  it on the first sign-in only).

**`sessions`**: `user_id`, `installation_id`, `family_id`, `token_hash`
(SHA-256, unique), `created_at`, `expires_at`, `rotated_at`, `replaced_by`,
`revoked_at`, `revoke_reason`.

- `revoke_reason`: `logout`, `reuse_detected`, `superseded`, `merged`,
  `account_deleted`, `admin`.
- Check: `revoked_at` and `revoke_reason` are both set or both null.
- Indexes on `family_id` and `user_id`.

**`user_merges`**: `source_user_id` (merged away), `target_user_id`,
`installation_id`, `strategy` (`keep_target`, `keep_source`, `merge`),
`created_at`, `notified_at`.

- Both users must belong to the same app; a user can be merged away only once;
  no self-merge.
- `notified_at` stays null until the app backend acknowledges the merge
  (delivery not implemented yet).

**`consents`**: append-only log of `(user_id, installation_id, purpose,
granted, policy_version, region, source, created_at)`. The current state is
the latest row per purpose. Table exists; API not implemented yet.

**`auth_nonces`**: `installation_id`, `nonce_hash` (SHA-256 hex, unique),
`created_at`, `expires_at`, `used_at`.

## Tokens

### Access token

- JWT signed with **EdDSA (Ed25519)**, lifetime 15 minutes
  (`ACCESS_TOKEN_TTL_SECONDS`).
- Header: `alg: EdDSA`, `kid` of the signing key.
- Claims: `sub` user id, `aud` app id, `ins` installation id, `plt` platform,
  `iss` (`JWT_ISSUER`), `iat`, `exp`.
- Verified without a database lookup. Public keys are published at
  `/.well-known/jwks.json`.
- **App backends** verify tokens with these public keys and must require
  `aud` = their own app id and `algorithms: ['EdDSA']`.
- Because verification is stateless, a token stays valid until it expires
  even after logout or account deletion (up to 15 minutes). Routes where this
  matters also check the user in the database (`GET /v1/me` does).

### Refresh token

- 32 random bytes, base64url. Only its SHA-256 hash is stored.
- Lifetime 90 days (`REFRESH_TOKEN_TTL_DAYS`), renewed on every rotation:
  an active user is never signed out.
- Rotated on every use: the old session is marked `rotated_at` and points to
  the new one via `replaced_by`.

### Signing keys

- `JWT_SIGNING_KEYS` holds a base64url-encoded JSON array of private Ed25519
  JWKs. The **first** key signs; the public halves of **all** keys are published.
- Generate with `pnpm keys:generate`. Dev and production keys are different;
  the production key is generated on the server.
- Rotation without signing anyone out:
  1. Append the new key at the **end** of the list and deploy. It is published
     but does not sign yet.
  2. Wait at least one hour (the JWKS cache time of app backends).
  3. Move the new key to the **front** and deploy. It now signs.
  4. Wait at least 15 minutes (access token lifetime) and remove the old key.

## Endpoints

All error responses have the shape `{ "error": "<code>", "message": "<text>" }`.
Invalid request bodies return `400 validation_failed`; exceeded rate limits
return `429`.

### `GET /.well-known/jwks.json`

Public keys for verifying access tokens. Cached for one hour
(`cache-control: public, max-age=3600`).

### `POST /v1/auth/anonymous`

First launch of an installation. Creates a user, the installation and a
session in one transaction. No auth. Rate limit 10/min per IP.

Request:

```json
{
  "appId": "uuid",
  "installationId": "uuid generated by the device",
  "platform": "android | ios",
  "appVersion": "1.0.0",
  "appBuild": "42",
  "osVersion": "15"
}
```

Response `201`, the **token pair** used by all auth endpoints:

```json
{
  "userId": "uuid",
  "accessToken": "jwt",
  "accessTokenExpiresIn": 900,
  "refreshToken": "opaque",
  "refreshTokenExpiresAt": "2027-01-24T19:29:34.737Z"
}
```

Errors:

| Status | Code                  | Meaning / client action |
|--------|-----------------------|-------------------------|
| 400    | `unknown_app`         | App unknown, disabled, or platform not registered |
| 409    | `installation_exists` | Installation id already taken: generate a new id and retry |

Installation ids are not secrets (they are inside access tokens and events),
so an existing id never yields tokens. If a response was lost and the retry
gets `409`, a new id is generated and an empty orphan user remains. That is
cheap and safe.

### `POST /v1/auth/refresh`

Exchanges a refresh token for a new token pair. No auth. Rate limit 30/min per IP.

Request: `{ "refreshToken": "..." }`. Response `200`: token pair.

Errors: `401 invalid_refresh_token` for every failure. The specific reason is
logged as a warning: `unknown_token`, `revoked:<reason>`, `reuse_detected`,
`expired`, `user_<status>`, `installation_reassigned`. For the client all of
them mean the session is dead and it must start over.

Algorithm, in one transaction:

1. Find the session by token hash and lock its row (`FOR UPDATE`), so parallel
   refreshes with the same token are serialized.
2. Unknown or revoked: reject.
3. Already rotated:
   - If it was rotated within the **grace window** (`REFRESH_REUSE_GRACE_SECONDS`,
     default 30) **and** the token issued in exchange is still unused, this is
     a retry after a lost response. The unused successor is revoked as
     `superseded`, and rotation continues.
   - Otherwise two parties hold the token: every live session of the family
     is revoked as `reuse_detected`, and the request is rejected. The
     rejection is thrown after the transaction commits, so the revocation is kept.
4. Expired, owner not active, or the installation now belongs to someone else:
   reject.
5. Insert a new session in the same family, expiring in 90 days. Mark the old
   one rotated (the first rotation time is kept, so retries cannot extend the
   grace window). Update the installation's `last_seen_at`.

Why the grace window: on a mobile network a response can be lost after the
server already rotated the token. Without the window the retry would look like
theft, and an anonymous user would lose their account forever.

### `POST /v1/auth/nonce`

Issues a one-time nonce for Google / Apple sign-in on the caller's
installation. Auth required. Rate limit 20/min per IP.

Response `200`: `{ "nonce": "base64url", "expiresAt": "ISO 8601" }`.

- Lifetime 10 minutes. Only the SHA-256 hex of the nonce is stored.
- Expired nonces of the installation are deleted on every new issue.
- **Google**: the app passes the raw nonce to Google; the token carries it raw
  and the server hashes it.
- **Apple**: the app passes the SHA-256 of the nonce to Apple; the token
  carries the hash, which matches the stored value directly.
- A nonce is consumed with a single atomic `UPDATE` (same installation, not
  used, not expired) **inside the sign-in transaction**. If the sign-in is
  refused (for example `409 account_exists`), the transaction rolls back and
  the nonce stays usable for the retry with the same provider token.

### `POST /v1/auth/google`

Links a Google account to the current user, or signs the device into the user
who already owns it. Auth required. Rate limit 10/min per IP.

Request:

```json
{
  "idToken": "Google ID token containing our nonce",
  "mergeStrategy": "keep_target | keep_source | merge"
}
```

`mergeStrategy` is omitted on the first attempt and set only when retrying
after `409 account_exists`.

Response `200`:

```json
{
  "result": "linked | already_linked | signed_in",
  "userId": "uuid",
  "tokens": null
}
```

`tokens` holds a new token pair only for `signed_in`, when the device switched
to another user. For `linked` and `already_linked` the device keeps its tokens.

Google token verification:

- Signature against Google's public keys (fetched and cached by jose).
- Issuer `https://accounts.google.com` or `accounts.google.com`.
- `aud` is one of the app's Google client IDs from `apps.oauth_clients`, any
  platform. If the app has none configured, every token is rejected.
- Algorithm `RS256` only, clock tolerance 30 seconds.
- A `nonce` claim is required.
- `email_verified` accepted as boolean or the string `"true"`.
- Name and picture are ignored.

Decision, in one transaction after locking the installation and consuming
the nonce:

| Situation | Result |
|-----------|--------|
| Account linked to the current user | `already_linked`, email details refreshed |
| Account not linked anywhere, current user has no Google account | `linked` |
| Account not linked anywhere, current user has another Google account | `409 provider_already_linked` |
| Account owned by user A, current user has any linked account | `409 already_signed_in`: sign out first |
| Account owned by user A, A is not active | `409 account_unavailable` |
| Account owned by user A, no `mergeStrategy` | `409 account_exists`, nothing changes |
| Account owned by user A, `mergeStrategy` given | merge, `signed_in` with A's tokens |

Other errors: `401 invalid_provider_token` (bad Google token or nonce; reason
logged as `google:<reason>`), `401 unauthorized` (the device no longer belongs
to the user, or the user is not active).

Merge (current anonymous user B into A):

1. Revoke B's live sessions as `merged`.
2. Set B to `merged`, `merged_into = A`.
3. Move the installation to A.
4. Insert a `user_merges` row with the strategy, `notified_at` null.
5. Issue a new session for A on this installation.

The platform's own data is not moved: B's history stays under B and is linked
to A through `merged_into`. Domain data is the app backend's business: it
will receive the merge with the chosen strategy (`keep_target` discard B's
progress, `keep_source` copy B's progress into A, `merge` combine both) and
act on it. Subscriptions are tied to the store account and come back through
purchase restore.

Parallel linking of the same account from two devices is caught by the unique
constraint and reported as `account_exists`.

### `POST /v1/auth/logout`

Signs out on this device. Auth required, no body.

Response `200`: token pair of a **fresh anonymous user** who now owns the
same installation.

- Revokes all live sessions of the user on this installation as `logout`.
- Keeps the installation id, so device history, data and the push token stay.
- The signed-out user stays active and can sign in again anywhere.
- The new user has no consents: the consent screen is shown again.

Errors: `409 no_linked_account` (anonymous users cannot sign out, they would
lose the account forever; the app should offer linking instead),
`401 unauthorized` (device reassigned or user not active).

### `GET /v1/me`

The current user. Auth required. Checks the user in the database, so a
merged or deleted user is rejected even with an unexpired access token.

Response `200`:

```json
{
  "userId": "uuid",
  "appId": "uuid",
  "installationId": "uuid",
  "platform": "android",
  "createdAt": "ISO 8601",
  "providers": [{ "provider": "google", "email": "player@gmail.com" }]
}
```

Errors: `401 unauthorized`.

### `GET /v1/consent`

The current policy, the latest decision per purpose and whether the consent
screen is needed. Auth required.

Response `200`:

```json
{
  "policy": { "region": "*", "mode": "optional", "version": "2026-10-29" },
  "status": "needs_decision | decided | not_required",
  "decisions": [
    { "purpose": "analytics", "granted": true, "policyVersion": "2026-10-29", "decidedAt": "ISO 8601" }
  ],
  "canAskAgainAt": "ISO 8601 or null"
}
```

- The policy is chosen by country, then `*`. The country is not known yet
  (no GeoIP), so `*` applies. An app without any policy asks everyone
  (version `0`, warning in the log).
- Screen purposes: `analytics` and `personalization`. Ads consent comes later
  through Google UMP.
- `decided` needs a decision for every screen purpose under the **current**
  policy version. A new version asks again.
- `not_required` (mode `none`): no screen; refusals from settings still count.
- `canAskAgainAt`: the last refusal plus `reprompt_after_days`.

### `POST /v1/consent`

Records decisions. Auth required. Rate limit 20/min per IP.

```json
{
  "decisions": { "analytics": true, "personalization": false },
  "policyVersion": "2026-10-29",
  "source": "first_launch | reprompt | settings",
  "decidedAt": "device time of the decision",
  "sentAt": "device time of sending"
}
```

- One append-only log row per purpose; the row time is the decision time.
- The decision time is shifted by the device clock error (`server now -
  sentAt`) and never lies in the future.
- Response: the new state, as in `GET`.
- The user must be active and still own the device.

## Error codes

| Code                      | Status | Client action |
|---------------------------|--------|---------------|
| `validation_failed`       | 400 | Bug in the client: fix the request |
| `unknown_app`             | 400 | Configuration error: wrong app id or platform |
| `unauthorized`            | 401 | Refresh the session and retry once; if refresh fails, start over |
| `invalid_refresh_token`   | 401 | Session is dead: sign up anonymously again |
| `invalid_provider_token`  | 401 | Request a new nonce and run the provider sign-in again |
| `installation_exists`     | 409 | Generate a new installation id and retry |
| `account_exists`          | 409 | Ask the person (if needed) and retry with `mergeStrategy` |
| `already_signed_in`       | 409 | Offer to sign out first |
| `provider_already_linked` | 409 | Another account of this provider is linked already |
| `account_unavailable`     | 409 | The existing account cannot be used (e.g. pending deletion) |
| `no_linked_account`       | 409 | Offer to link Google / Apple before signing out |
| `internal_error`          | 500 | Retry later |

| Variable                      | Default         | Meaning |
|-------------------------------|-----------------|---------|
| `JWT_ISSUER`                  | `apps-platform` | `iss` claim of access tokens |
| `JWT_SIGNING_KEYS`            | required        | Base64url JSON array of private Ed25519 JWKs; first one signs |
| `ACCESS_TOKEN_TTL_SECONDS`    | 900             | Access token lifetime |
| `REFRESH_TOKEN_TTL_DAYS`      | 90              | Refresh token lifetime, renewed on rotation |
| `REFRESH_REUSE_GRACE_SECONDS` | 30              | Window for retrying a rotated refresh token |

## Security notes

- Installation ids are not secrets and never yield tokens.
- Refresh tokens and nonces are stored only as SHA-256 hashes. Plain SHA-256
  is enough because both are 32 random bytes and cannot be brute-forced.
- Only expected algorithms are accepted: `EdDSA` for our tokens, `RS256` for Google.
- An empty list of allowed client IDs rejects every provider token, because
  otherwise the audience check could be skipped.
- Every failure reaches the client as one code per category; specific reasons
  are logged as warnings.
- Rows that are read, checked and then changed are locked first: the session
  on refresh, the installation on logout and sign-in.
- Rate limits are per IP and in memory. Behind a proxy the real client IP must
  be taken from the proxy header (not configured yet).

## Not implemented yet

- **Apple sign-in** (iOS only): ID token verification against Apple's keys,
  exchange of the authorization code for an Apple refresh token (only when the
  account is linked for the first time, before the transaction), encryption of
  that token with `DATA_ENCRYPTION_KEY` (AES-256-GCM), Apple server-to-server
  notifications. One developer key for all apps in `.env` (`APPLE_TEAM_ID`,
  `APPLE_KEY_ID`, `APPLE_PRIVATE_KEY`). Waiting for an Apple Developer account.
- **Device details update** with analytics consent, and geo from IP.
- **Account deletion**: `DELETE /v1/me`, scheduled erasure in every module,
  Apple token revocation, notifying the app backend.
- **Merge delivery** to app backends (signed webhook with retries, sets `notified_at`).
- **Cleanup job** for nonces of abandoned installations.
- **Trusted proxy** configuration for rate limits behind Caddy.
