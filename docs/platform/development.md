# Platform development

How to run, change and test the platform server locally.

## Requirements

- **Node.js 24** via nvm. The repository root has `.nvmrc`, so `nvm use` in
  the project picks the right version.
- **pnpm 12** (pinned in the root `package.json` as `packageManager`).
  Install with `npm install -g --allow-scripts=pnpm pnpm`.
- **Docker** with Compose, for the local Postgres.
- `jq` and `uuidgen` are handy for manual requests with curl.

Build scripts of dependencies are blocked by default. When pnpm reports
ignored builds (for example `esbuild`, needed by `tsx`), run
`pnpm approve-builds` and allow them. The decision is stored in the repository.

## First setup

```bash
# 1. Local database
cd infra
cp .env.example .env
docker compose -f docker-compose.dev.yml up -d
docker compose -f docker-compose.dev.yml ps        # wait for "healthy"

# 2. Dependencies (from the repository root)
cd ..
pnpm install

# 3. Server configuration
cd platform
cp .env.example .env
pnpm keys:generate                                  # paste the printed line into .env

# 4. Database schema and a demo app
pnpm db:migrate
pnpm db:seed                                        # prints the demo app id

# 5. Run
pnpm dev
curl http://127.0.0.1:3000/health                   # {"status":"ok","database":"ok"}
```

## Local database

`infra/docker-compose.dev.yml` runs Postgres 18 only. The server runs on the
host for instant reloads.

- The port is bound to `127.0.0.1:5432`, never to the network.
- Data lives in the named volume `pgdata` and survives restarts.
- Credentials come from `infra/.env`. Compose refuses to start if a variable
  is missing.

| Action | Command (from `infra/`) |
|--------|-------------------------|
| Start | `docker compose -f docker-compose.dev.yml up -d` |
| Stop, keep data | `docker compose -f docker-compose.dev.yml down` |
| Stop and erase data | `docker compose -f docker-compose.dev.yml down -v` |
| SQL shell | `docker compose -f docker-compose.dev.yml exec postgres psql -U platform -d platform` |

Useful psql commands: `\dn` schemas, `\dt identity.*` tables, `\d <table>`
columns and constraints, `\dT <schema>.*` enums, `\q` exit.

## Configuration

The server reads environment variables once at startup and validates them
with zod (`src/core/config.ts`). On any problem it prints every invalid
variable and exits. Locally Node loads `platform/.env` (`--env-file`); in
Docker the variables come from Compose.

| Variable | Default | Meaning |
|----------|---------|---------|
| `NODE_ENV` | `development` | `development`, `production` or `test` |
| `HOST` | `127.0.0.1` | Listen address; `0.0.0.0` inside Docker |
| `PORT` | `3000` | Listen port |
| `LOG_LEVEL` | `info` | `silent` … `trace`; development logs are pretty-printed |
| `DATABASE_URL` | required | `postgres://user:password@host:5432/db` |
| `JWT_ISSUER` | `apps-platform` | `iss` of access tokens |
| `JWT_SIGNING_KEYS` | required | Generated by `pnpm keys:generate` |
| `ACCESS_TOKEN_TTL_SECONDS` | `900` | Access token lifetime |
| `REFRESH_TOKEN_TTL_DAYS` | `90` | Refresh token lifetime |
| `REFRESH_REUSE_GRACE_SECONDS` | `30` | Retry window for a rotated refresh token |

When adding a variable: add it to the schema in `config.ts`, to
`.env.example`, and to your own `.env`. Never put real secrets into
`.env.example`.

## Scripts

All run from `platform/`.

| Script | What it does |
|--------|--------------|
| `pnpm dev` | Run with `tsx watch`, reload on save |
| `pnpm typecheck` | Type-check source, tests and scripts |
| `pnpm test` | Run all tests once |
| `pnpm test:watch` | Re-run tests on save |
| `pnpm build` | Compile `src/` (without tests) to `dist/` |
| `pnpm start` | Run the compiled server (production) |
| `pnpm db:generate --name <name>` | Generate a migration from schema changes |
| `pnpm db:migrate` | Apply pending migrations |
| `pnpm db:seed` | Create the `demo` app (refuses to run in production) |
| `pnpm keys:generate` | Print a new `JWT_SIGNING_KEYS` line |

Always run both `pnpm test` and `pnpm typecheck`: Vitest does not check types,
and the type checker does not run code.

## Database schema and migrations

- Tables are defined in `src/modules/<module>/schema.ts`; drizzle-kit picks up
  every module automatically.
- Each module has its own Postgres schema, listed in `schemaFilter` in
  `drizzle.config.ts`. A new module's schema must be added there.
- Workflow: change `schema.ts` → `pnpm db:generate --name <what_changed>` →
  read the generated SQL → `pnpm db:migrate` → commit `migrations/` (including
  `meta/`).
- **Never edit a committed migration.** Fix mistakes with a new migration.
- The migration script (`src/core/migrate.ts`) is compiled with the server and
  runs in the container before startup in production.
- Name constraints explicitly when they are composite: Postgres truncates
  names longer than 63 characters, and explicit names make errors readable.

Current migrations: `0000_init_apps`, `0001_init_identity`,
`0002_add_superseded_revoke_reason`, `0003_add_auth_nonces`.

## Tests

- Vitest, integration style: tests build the app with `buildApp()` and send
  requests through `server.inject()`, without a real port.
- Tests use a separate database `<name>_test` on the same Postgres server
  (`platform_test` locally). It is created on the first run; migrations are
  applied before every run.
- Every test file resets the database in `beforeEach`
  (`TRUNCATE apps.apps CASCADE` empties everything) and seeds a test app.
- Test files run one after another (`fileParallelism: false`) because they
  share the database.
- A throwaway signing key is generated per run; tests need no secrets.
- Server logs are silent in tests. Show them with
  `TEST_LOG_LEVEL=error pnpm test`.
- Time-dependent cases move timestamps in the database (`rotated_at`,
  `expires_at`) or fake the clock (`vi.useFakeTimers({ toFake: ['Date'] })`)
  instead of waiting.

Helpers in `test/`:

| File | Provides |
|------|----------|
| `helpers.ts` | `resetDatabase`, `seedApp`, `signUpViaApi`, `linkFakeGoogleAccount` |
| `fake-google.ts` | `installFakeGoogle`, `signFakeGoogleToken` with any claims, attacker key |

Tests live next to the code as `*.test.ts`. New behaviour comes with tests in
the same commit.

## Adding a module

1. Create `src/modules/<name>/` with `schema.ts` (tables in its own
   `pgSchema`), `service.ts` (logic) and `routes.ts` (a Fastify plugin).
2. Add the schema name to `schemaFilter` in `drizzle.config.ts`.
3. Reference users through the composite key `(user_id, app_id)` → `identity.users`.
4. Register the routes in `src/app.ts`.
5. Other modules use your service functions, never your tables.
6. Generate and apply the migration, write tests, document the module in
   `docs/platform/<name>.md` and update `docs/platform/status.md`.

## Conventions

- All code comments and documentation are in English.
- TypeScript is strict. Relative imports end with `.js`.
- Validate everything that comes from outside (env, requests, tokens) with zod.
- Expected errors are `AppError(status, code, message, internalReason?)`.
  Clients branch on `code`; the internal reason is only logged.
- Transactions are short: no network calls inside them.
- Read-check-write sequences lock the row first (`.for('update')`).
- Commits follow Conventional Commits with a scope, for example
  `feat(platform): ...`, `fix(platform): ...`, `test(platform): ...`,
  `docs: ...`, `chore(infra): ...`. Every commit has a short description
  listing what changed.

## Manual requests

```bash
API=http://127.0.0.1:3000
APP_ID=<demo app id>

# Anonymous sign-up
curl -s -X POST $API/v1/auth/anonymous -H 'content-type: application/json' \
  -d "{\"appId\":\"$APP_ID\",\"installationId\":\"$(uuidgen)\",\"platform\":\"android\",\"appVersion\":\"1.0.0\",\"appBuild\":\"1\",\"osVersion\":\"15\"}" | jq

# Current user
curl -s $API/v1/me -H "Authorization: Bearer <accessToken>" | jq

# Decode the payload of an access token
echo '<accessToken>' | cut -d. -f2 | base64 -d 2>/dev/null; echo
```

Tokens and keys from a local setup may be shared for debugging. Never share
anything from a production server.

## Google sign-in (local)

One Google Cloud project for development (`apps-platform-dev`), configured in
**Google Auth Platform**:

- Audience **External**, testing mode. Only accounts listed under
  Audience → Test users can sign in.
- **Web client**: its client ID is the token audience. It goes to
  `GOOGLE_WEB_CLIENT_ID` in `platform/.env` (then `pnpm db:seed`) and to
  `GOOGLE_SERVER_CLIENT_ID` in `sdk/flutter/example/dev.json`. The client
  secret is not used anywhere.
- **Android client**: package `com.renvix.renvix_sdk_example` and the SHA-1
  of the debug key. Not written anywhere: Google matches it by package and
  signature. Get the SHA-1 with `./gradlew signingReport` in
  `sdk/flutter/example/android`.

The emulator needs a Google account (Settings → Accounts) that is a test user.

Release builds will need more Android clients: the upload key and the Play
app signing key.

Common failures:

| Symptom | Cause |
|---------|-------|
| `credential_error` mentioning the developer console | Wrong SHA-1 or package, Android client ID used instead of the web one, or the client is not active yet |
| `no_google_account` | No Google account on the device |
| `invalid_provider_token` from the server | Web client ID not registered (`db:seed`); the server log has the reason |
